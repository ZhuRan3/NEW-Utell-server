# 跨端公开契约治理规范

> 状态：执行中（2026-08-23）
> 适用范围：NEW-Utell-phone、NEW-Utell-server，以及消费 `integration-profile` 的 Connector 工程

## 目的

本文件是跨端契约的长期治理规则。它约束契约的真源、确认、版本、同步、验证和新会话交接，防止 Phone、Relay、Connector 各自维护一份不一致的协议。

## 权威层级

```text
PRD
  -> Q&A / 需求确认台账
  -> 架构基线
  -> integration-profile
  -> Harness 契约/fixtures/mocks/scenarios
  -> 生产实现
  -> 测试证据与发布门禁
```

- PRD 是产品语义真源；用户明确回答写入 Q&A 后，才可改变已确认语义。
- 架构基线只描述边界和职责，不替代机读契约。
- `integration-profile` 是跨端公开契约入口；Connector、Phone、Relay 只消费其中的公开字段和行为。
- 任一内部数据库、Pi RPC、Prompt、文件路径或私有 API 不得写入公开契约。

## 契约真源和同步规则

- 两个仓库都必须存在 `harness/契约/integration-profile.yaml`。
- 两个文件必须逐字节一致；契约相关 Schema、错误码、兼容矩阵、测试向量索引和公开示例也必须保持同路径、同内容。
- 契约变更必须在两个仓库同一工作批次同步，不能先改一边再等待另一边补齐。
- 每次同步必须记录文件校验和；后续 CI 必须阻止两边校验和不一致。
- 当前 `integration-profile` 为 `pending`，在 E2EE、消息封套、错误码、Projection、Card Command 和兼容范围冻结前，不得作为生产实现依据。

## 状态和版本

契约文件必须包含 `profile_version` 和 `status`：

- `pending`：需求或技术细节未冻结，只能用于讨论和 Spike。
- `proposed`：字段和行为已整理，等待用户/跨端 Owner 接受。
- `approved`：可用于生产实现和契约测试。
- `deprecated`：保留兼容说明，不得新增依赖。

采用 SemVer：

- `0.x`：首个 P0 契约冻结前的开发期版本；不得假设兼容性。
- `1.0.0`：P0 公开契约首次冻结。
- 主版本：删除字段、改变状态语义、改变失败语义或破坏既有兼容范围。
- 次版本：只增加向后兼容字段或场景，并明确默认行为。
- 修订版本：只修正文案、示例或不改变语义的勘误。

## 变更流程

1. 先在 `文档/需求对齐/需求问答记录.md` 新增一个 Q&A 编号；一次只处理一个独立问题。
2. 先复核 PRD；若 PRD 已明确，按 PRD 登记；若 PRD 未明确，等待用户确认，不得用默认值代替。
3. 用户确认后，同步 PRD、两端需求确认台账、架构基线和技术选型/Spike 记录。
4. 修改两端 `harness/契约/` 的同名文件，更新 `profile_version` 和变更说明。
5. 为每个行为增加最小合成 fixture、mock 故障点和 Given/When/Then 场景，并建立 AC 到场景的映射。
6. 运行静态检查、契约测试和故障场景；证据写入 `harness/evidence/YYYY-MM-DD/`，不得包含业务正文、私钥或真实标识。
7. 只有契约状态为 `approved` 且两端校验和一致，才允许进入生产实现；未批准内容只能进入 `spikes/`。

## 时间盒和进度口径

时间盒是推进上限，不是把未解决的问题强行关闭的截止日期：

| 阶段 | 建议时间盒 | 完成条件 |
| --- | --- | --- |
| G0 真源同步 | 每次 30 分钟内完成盘点 | 两端 PRD、台账、Q&A、基线无已知状态漂移 |
| G1 需求对齐 | 每个独立问题 1 次工作会话 | 有用户原文、结论、影响文件和回滚条件 |
| G2 技术 Spike | 每个高风险 Spike 最多 1 个工作日 | 原始结果、失败样本、解释和决策影响齐全 |
| G3 契约冻结 | Spike 通过后 1–2 次工作会话 | `integration-profile` 为 `approved`，两端校验和一致 |
| G4 Harness P0 | 首个纵向切片 1 个工作日；完整 P0 场景 2–3 个工作日 | 场景可重复运行并产生脱敏证据 |
| G5 生产纵向切片 | Harness 首个切片通过后开始 | Phone、Relay、Connector 对同一契约互操作 |

每个工作会话结束必须更新 `文档/工作进度/开发进度与会话交接.md`：完成项、进行中、阻塞项、证据位置、下一步和预计时间盒必须齐全。

## 新会话交接规则

新会话开始时必须按以下顺序读取：

```text
AGENTS.md
-> PRD
-> 文档/架构与契约/跨端公开契约治理规范.md
-> 文档/工作进度/开发进度与会话交接.md
-> 文档/需求对齐/需求确认台账.md
-> 文档/需求对齐/需求问答记录.md
-> 文档/架构与契约/架构基线.md
-> harness/harness.yaml
-> harness/契约/integration-profile.yaml
-> 开发规则规范/07-人类可读进度与技术沟通规范.md
-> 文档/交流记录/README.md
-> 文档/交流记录/项目驾驶舱.md
```

新会话必须先按两层格式报告当前阶段和 Git 工作树，再开始修改：第一层是项目驾驶舱，第二层是测试站证据和技术学习条。遇到未确认的产品或技术决策时，一次只向用户提一个问题；在答案写入 Q&A 前不得修改实现或把建议写成默认值。

## 禁止事项

- 单边修改公开契约。
- 在 `pending`/`proposed` 契约上开始生产实现。
- 为测试复制一份手机专用或 Relay 专用私有协议。
- 把 Relay ACK 当成 Connector 持久接收、事务提交或 Projection 成功。
- 把真实 Capture、私钥、账号标识或可还原业务内容写入 fixture、日志和证据。
- 用“暂时这样”“以后再统一”跳过 Q&A、版本和证据记录。
