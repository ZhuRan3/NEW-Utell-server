# 下一项技术栈冻结前决策：Noise 首发 Pattern 选择什么？

> 文档状态：学习讲义与决策建议，尚未替代 D4 正式 Q&A
> 建议结论：首发采用 `Noise_XX_25519_ChaChaPoly_SHA256`
> 适用边界：NEW-Utell 手机与 PC Connector 的应用层 E2EE；Relay 只转发密文
> 更新时间：2026-08-24

## 先看全貌

### 根本问题

NEW-Utell 要让手机把业务密文送到个人电脑 Connector。公网 Relay 可以帮忙接线，但不能成为业务明文的保管者。第一次建立加密管道时，手机和 Connector 既要确认“我们各自持有哪一个长期身份”，又要接上现有的扫码、一次性 token 和用户指纹核对流程。

这里的关键决策不是“选哪种加密算法”这么简单，而是“双方第一次见面时，静态身份在什么时候出现、需要几个消息、谁必须提前知道谁”。

### 本讲义的路线

1. 先定位 Noise 在四层链路中的位置。
2. 读懂协议名和握手脚本。
3. 逐步运行 `XX` 与 `IK`。
4. 用扫码配对场景对齐两者的前提。
5. 比较安全属性、复杂度、失败路径和未来演进。
6. 给出首发建议与冻结前必须补齐的证据。

### 边界

本文不选择 Relay 的 Go/Caddy 栈，不设计 Connector 内部数据库，不把 Noise 当成账号体系，也不把一次性 token 当成静态公钥。Noise 证明的是密码学上的密钥持有和会话完整性；“这把公钥是不是用户正在看的那台电脑”仍要由二维码、指纹和用户确认完成。

## 第一章：先把 NEW-Utell 的工作链路放回脑中

手机 → Relay → Connector → Utell Pi 是四层链路。业务权威在 Connector，手机只保留会话内存，Relay 只见密文。Noise 位于手机和 Connector 两个端点之间，Relay 在中间经过但没有解密钥匙。

**生动例子：三层门。** Relay 像只看门牌、不拆信的接线总机；Noise 像手机和电脑各自持有的保险箱锁；二维码和指纹核对像用户在两台设备前确认“我开的确实是这间房”。总机可以把信转错或拒收，但不能读懂保险箱里的内容。

当前项目资料已经确认：

- 手机端是 SwiftUI + iOS 17+，Connector 侧候选参照实现是 Rust `snow`。
- 配对流程是扫码、显示公钥指纹、用户确认、一次性 token（建议 5 分钟且仅用一次）。
- Relay ACK 只表示 Relay 收到并尝试路由，不代表 Connector 持久接收。
- D4 方向已经选 Noise，但 pattern、握手角色、rekey 和跨端向量仍待冻结。

## 第二章：Noise 名字到底在说什么

`Noise_XX_25519_ChaChaPoly_SHA256` 是四段式协议名：

| 部分 | 白话含义 | 在 NEW-Utell 中的职责 |
|---|---|---|
| `Noise` | 使用 Noise Protocol Framework | 规定握手状态机和安全属性 |
| `XX` | 握手 Pattern | 规定消息顺序、何时交换静态公钥 |
| `25519` | X25519 Diffie-Hellman | 让双方算出旁观者算不出的共享秘密 |
| `ChaChaPoly` | ChaCha20-Poly1305 AEAD | 加密并检测篡改 |
| `SHA256` | SHA-256 哈希/HKDF 搅拌 | 滚动更新握手 hash、chaining key 和会话密钥 |

`XX` 和 `IK` 是“对话脚本”，不是两套完全不同的密码学。两者都可以使用同一个 `25519 + ChaChaPoly + SHA256` 套件，主要差别在静态身份何时发送。

### 握手脚本中的符号

- `e`：发送临时公钥。本次会话专用，用完即弃。
- `s`：发送静态公钥。它是设备的长期密码学身份，不是私钥。
- `ee`：双方临时公钥做 DH。
- `es` / `se`：一方临时公钥与另一方静态公钥做 DH；字母顺序按 initiator/responder 角色解释。
- `ss`：双方静态公钥做 DH。

每个 DH 结果都会进入滚动的 `chaining key`，随后由 AEAD 加密静态公钥和 payload。成功解密并不等于“用户看过指纹”，它首先证明对端确实持有与所发公钥匹配的私钥。

## 第三章：XX 是怎样跑起来的

官方脚本是：

```text
XX:
  -> e
  <- e, ee, s, es
  -> s, se
```

把它翻成三句人话：

1. 手机先发一张本次会话的临时“面具”。这条消息不要求手机提前知道 Connector 的静态公钥。
2. Connector 回自己的临时“面具”，双方先做 `ee`，再把 Connector 的静态公钥加密发出，并用 `es` 证明自己持有对应私钥。
3. 手机收到并验证后，再把自己的静态公钥加密发出，用 `se` 让 Connector 也完成验证。

### 为什么它适合首次扫码配对

二维码可以先带一次性 token、Relay 地址、Connector 名称和用于展示的指纹。token 负责“这次配对是否被授权”，XX 负责“握手中的静态公钥和私钥是否匹配”，用户指纹核对负责“我是否把这把公钥绑定到眼前这台设备”。三者各自承担一层责任，链路清楚。

Noise 规范给出的身份隐藏等级是：XX 的 initiator 静态身份为 8 级、responder 为 1 级（数值越高，旁观者越难确认身份）。这不是“完全匿名”：Connector 的静态公钥在第二条消息中出现并且会被加密，手机的静态公钥延后到第三条消息才出现。

**这里简化了：**“8 级/1 级”是 Noise 规范的相对属性表，不是 NEW-Utell 的隐私评分，也不是实测概率。项目仍需通过固定向量和实际传输封装验证。

## 第四章：IK 是怎样跑起来的

官方脚本是：

```text
IK:
  <- s
  ...
  -> e, es, s, ss
  <- e, ee, se
```

`<- s` 表示 initiator 在握手开始前已经知道 responder 的静态公钥。于是手机第一条消息就可以：

1. 发新的临时公钥 `e`；
2. 用手机临时私钥和 Connector 静态公钥做 `es`；
3. 加密发送手机静态公钥 `s`；
4. 再用双方静态密钥做 `ss`；
5. 第一条消息可携带一个 0-RTT 的加密 payload。

Connector 回第二条消息完成 `ee` 和 `se`，双方进入 transport。消息少半圈，开场更快。

### IK 的硬前提为什么不能含糊

如果手机拿到的是攻击者伪造的 Connector 公钥，IK 仍可能建立一条“密码学上自洽”的会话，只是建立给了错误对象。换句话说，IK 不会自动替用户判断“这把公钥是不是我扫码看到的那台电脑”。

因此，IK 需要在握手前可靠绑定静态公钥，例如：已完成一次 XX 配对、通过可信安装渠道分发、或把公钥作为已认证配置的一部分。把公钥仅仅塞进 Relay 转交的二维码而不做指纹/签名绑定，会把 Relay 或二维码来源提升成新的信任根，改变当前“Relay 只做蒙眼路由”的边界。

## 第五章：XX 与 IK 的正面对比

| 维度 | XX | IK |
|---|---|---|
| 消息数 | 3 条，1.5 RTT | 2 条，1 RTT |
| 首次开场 | 不需要提前知道对端静态公钥 | initiator 必须提前知道 responder 静态公钥 |
| 双方静态身份 | 握手中互相交换并验证 | initiator 静态身份首条发送，responder 静态公钥是前置知识 |
| 0-RTT payload | 支持性弱，不能依靠未完成握手的业务数据 | 支持第一条消息携带加密 payload |
| 身份隐藏 | initiator 8，responder 1 | initiator 4，responder 3 |
| 与扫码+token | 先授权、再交换、再指纹确认，顺序自然 | 需要先解决公钥如何可信到达手机 |
| 实现复杂度 | 一个直接脚本，回退路径少 | 若做 Pipes，需要 IK、XXfallback、协商、试解密和公钥轮换处理 |
| 首发失败面 | 多半个 RTT；主要是网络超时和指纹/ token 失败 | 快，但公钥错绑会成为结构性风险 |
| 未来价值 | 可靠基线，可作为首次配对 | 适合已绑定后的快速重连优化 |

### 生动例子：陌生人和老熟人

XX 像第一次在线下见面：两人各带一张临时名片，先交换临时信息，再在上锁的信封里交出长期身份证，最后互相确认。多说一句话，但不需要提前认识。

IK 像老熟人打电话：手机通讯录里已经存着 Connector 的长期号码，第一句暗号就能加密说话，速度快，还可以在第一句顺便交代事情。问题是通讯录里那串号码必须真的来自上次可信见面，而不能是中间人塞进去的。

## 第六章：扫码、token、指纹和 Noise 如何拼成一条工作链路

推荐的首发链路如下：

1. Connector 首次启动生成并安全保存静态密钥对，显示二维码。
2. 二维码携带短期一次性 token、Relay 地址、Connector 展示名和指纹信息；token 过期或使用过即拒绝。
3. 手机扫码后通过 Relay 找到 Connector，但 Relay 只登记配对和路由元数据，不持有端点解密钥匙。
4. 手机作为 initiator 发起 `Noise_XX_25519_ChaChaPoly_SHA256`。
5. 双方在 XX 的消息中交换静态公钥并完成密钥持有证明。
6. 手机和 Connector 展示同一静态公钥指纹，用户确认后才把 pairing 绑定为有效。
7. Noise handshake 完成，进入 transport；此后业务请求在手机和 Connector 端点加密，Relay 只转发密文。
8. 任一 token 失效、指纹不符、公钥轮换未确认、重放或篡改，都拒绝建链并回到未配对/重新配对状态。

### “互相确认静态身份”必须拆成两件事

1. **密码学确认：**Noise 的 `es/se/ss` 让对端证明自己持有对应私钥，握手 hash 防止消息被替换。
2. **产品信任确认：**用户把二维码看到的 Connector 指纹与设备屏幕/可信展示进行核对；手机把这次确认绑定到 pairing。

只有两层都完成，才可以把状态提升为 `READY`。Noise 本身不能代替用户核对设备归属。

## 第七章：为什么首发不直接把 IK 和 Noise Pipes 一起塞进来

官方 Noise 规范提供 Noise Pipes：首次用 XX，缓存 responder 静态公钥后用 IK 走 0-RTT；如果公钥失效，再使用 `XXfallback`。这是一条合理的演进路线，但它不是“把 IK 改一个枚举值”那么简单：双方必须对模式、协议名、fallback 角色和试解密策略达成一致。

`XXfallback` 与普通 `XX` 的协议名不同，协议名参与初始握手 hash；一端把它当 XX、另一端把它当 XXfallback，消息可能无法解密。libp2p 的公开讨论记录了这一类兼容性陷阱，并最终因收益有限、实现复杂度和跨实现兼容负担，第一版只保留 XX。

这对 NEW-Utell 的启示是：

- 首发业务消息必须等握手完成和 Connector 身份确认后再发送，IK 的 0-RTT 速度收益不会直接转化成业务体验收益。
- 当前项目是手机与固定个人电脑的一对一配对，不是大量陌生节点的通用 P2P 网络；多半个 RTT 通常不是主要瓶颈。
- 先冻结单一、可互操作的 XX 向量，未来在“已完成可信配对”的重连路径单独评估 IK，而不是首发同时实现多个模式。

**取舍：**首发推荐 XX 牺牲约半个握手往返，换取更简单的信任链、更少的协商/回退分支和更好的跨语言可验证性。这个取舍只有在实测显示握手延迟已经成为 P0 瓶颈时才值得反转。

## 第八章：实现与验证必须冻结什么

`Noise_XX_25519_ChaChaPoly_SHA256` 只是起点，不是完整跨端契约。进入生产实现前，至少要冻结：

| 冻结项 | 必须写清的内容 |
|---|---|
| 角色 | 手机固定 initiator，Connector 固定 responder；重连是否保持角色不变 |
| 协议名 | 双端逐字节一致的完整 ASCII 名称 |
| Prologue | 是否绑定 pairing_id、token 派生上下文、版本；禁止把未认证可变数据放入 prologue |
| 静态密钥 | 生成、Keychain/Connector 存储、轮换、撤销、指纹编码和展示 |
| token | 有效期、一次性消费、重放拒绝、与 pairing 的绑定方式 |
| payload | 握手 payload 是否为空；业务数据不得在身份确认前进入首发路径 |
| transport | nonce/counter、最大消息、方向键、错误分类、关闭语义 |
| rekey | 触发条件、双方同步信号、失败后是否重建握手；Noise 规范把 rekey 留给应用决定 |
| 失败处理 | token 失效、指纹不符、静态公钥变更、AEAD 失败、超时、断线重连 |
| 向量 | 每条握手消息 hex、握手 hash、transport 密文、错误样本；禁止私钥和业务原文进入证据 |

### 现有 Spike 的最小验收

- Swift 侧候选库支持目标套件和 `XX`，不自研密码原语。
- 与 Rust `snow` 对同一固定密钥/随机数/空 payload 产生一致消息、握手 hash 和 transport 密文。
- iOS 17 target 编译通过。
- 过期/已用 token、重放、篡改、指纹不符、公钥轮换均拒绝建链。
- 手机、Connector、Relay 日志和 fixture 不出现私钥或业务原文。
- 本机 Spike 结果已回写到 Phone Noise Spike 和证据摘要，并同步两端 `integration-profile.yaml`；Connector 共同验收完成前保持 `status: pending`。

## 书级回顾

Noise 是“用握手脚本组织 DH、再进入 AEAD transport”的协议框架。`XX` 让双方首次见面时现场交换并验证静态身份，3 条消息、1.5 RTT；`IK` 依赖 initiator 预先可靠持有 responder 静态公钥，2 条消息、1 RTT，并可带 0-RTT payload。NEW-Utell 的扫码、一次性 token 和指纹确认天然更贴近 XX：token 负责一次性授权，指纹负责用户信任，XX 负责端点密钥持有和会话建立。因此首发建议冻结 `Noise_XX_25519_ChaChaPoly_SHA256`，把 IK/Noise Pipes 留作已配对重连的后续 Spike。

### 值得深挖的方向

- Swift `swift-noise` 与 Rust `snow` 的真实互操作向量，决定实现是否可落地。
- 公钥轮换与撤销：Connector 重装、Keychain 清除、设备替换时如何强制重新扫码。
- Prologue 与 pairing/token 绑定，避免上下文混淆或把可变数据误当成协议身份。
- transport rekey、nonce、消息上限与 Relay 背压之间的组合行为。
- 已配对重连是否真的值得 IK：用真机网络条件和 P95 指标测量，而不是凭直觉。
