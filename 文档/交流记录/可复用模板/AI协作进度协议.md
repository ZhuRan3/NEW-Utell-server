# AI 协作进度协议（可复用模板）

> 用途：把 AI Agent 的工程执行过程，转换成项目拥有者能快速理解和控制的进度信息。
> 适用：软件、硬件配套工具、自动化脚本、网页、移动端、后端和跨端项目。
> 原则：不替代 PRD、架构文档和测试报告；它是连接“工程真相”和“人类理解”的沟通层。

## 一、核心原理

### 1. 两个世界，中间加一层翻译

工程世界有代码、日志、测试、提交和协议；项目拥有者关心目标、风险、进度和是否可以继续。AI 协作进度协议负责把前者压缩成后者，同时保留证据入口。

```text
工程真源（代码 / PRD / 契约 / 测试）
              ↓ 事实提取与白话解释
人类可读控制层（驾驶舱摘要 / 测试站证据）
              ↓ 用户确认或暂停
下一步 Agent 行动
```

### 2. 进度不是百分比，而是状态和门

“完成 70%”很容易误导，因为不同部分的风险不一样。协议使用以下状态：

- `已证实`：有代码、测试、运行结果或 Owner 签收。
- `待证据`：方向合理，但还缺测试、环境或集成证据。
- `待决策`：有多个合理选项，需要项目拥有者选择。
- `待开发`：方向已确定，但尚未实现。

阶段只有在放行条件满足后才能前进。测试通过不自动等于阶段通过。

### 3. 任何结论都要标出证据边界

每次汇报至少说明：证据在哪里、它能证明什么、它不能证明什么。这样可以把“模型的合理猜测”和“项目已经验证的事实”分开。

### 4. 人和 Agent 的职责不同

- 项目拥有者：决定目标、产品取舍、风险接受和阶段放行。
- Agent：阅读资料、制定计划、修改文件、运行检查、整理证据和提出风险。
- 自动测试/构建/运行环境：提供尽量客观的通过或失败信号。

Agent 可以提出“建议继续”，但不能替用户把 `待决策` 改成“已批准”。

### 5. 保留专业语言，并提供学习阶梯

协议不把专业名词全部替换成口语。首次出现时保留中文、英文原词、缩写和必要技术参数，再按以下顺序教学：

```text
原词与英文全称
  -> 10 秒白话定义
  -> 在当前项目中负责什么
  -> 忽略它会有什么后果
  -> 当前处于什么状态、有何证据
  -> 用户现在需要判断什么
```

每次驾驶舱最多引入 1–3 个新术语，避免一次灌输过多；已经解释过的术语可直接使用，并链接到 `glossary.md`。原始字段名、错误码、协议名、命令和指标必须保留，不能只剩模糊的中文转述。

## 二、两层汇报格式

### 第一层：项目驾驶舱

目标是让用户在 30 秒内知道项目在哪里。

```markdown
## 驾驶舱摘要

- 我们在哪里：<阶段 / 任务>
- 我们要解决什么：<一句用户能理解的话>
- 当前一句话状态：<已完成什么，正在等什么>
- 当前主任务：<现在只推进哪一件事>
- 已经走过的路：<已完成的阶段或里程碑>
- 前方路障：<阻塞 / 待证据 / 待决策>
- 下一站：<下一阶段及其目的>
- 能否继续：<可以继续 / 需要用户确认 / 暂停等待外部条件>
- 需要用户回答：<最多一个问题；没有则写“无需回答”>

### 本次技术学习条（最多 1–3 个新术语）

| 专业名词 | 10 秒解释 | 在本项目中的作用 | 当前状态 |
| --- | --- | --- | --- |
| <中文名（English full name, ACRONYM）> | <一句白话> | <具体模块或链路> | <已证实 / 待证据 / 待决策 / 待开发> |
```

### 第二层：测试站证据

目标是让用户在需要时核对判断依据。

```markdown
## 测试站证据

| 项目 | 内容 |
| --- | --- |
| 测试目的 | 要验证的一个风险或假设 |
| 测试条件 | 设备、版本、网络、输入、并发量等 |
| 实际操作 | Agent 执行的命令或步骤 |
| 观察结果 | 通过、失败和异常样本 |
| 证据位置 | 文件、日志、截图、报告或提交号 |
| 可以证明什么 | 结果成立的范围 |
| 不能证明什么 | 尚未覆盖的范围 |
| 放行标准 | 进入下一阶段前必须满足的条件 |
| 决策影响 | 继续、补证据、改方案或停止 |
| 回滚方式 | 结论被推翻时回到哪里 |
```

需要深入某个术语时，在测试站后补一张学习卡：

```markdown
### 技术学习卡：<Term>

- 中文与英文：<中文名 / English full name / abbreviation>
- 它属于什么：<协议 / 服务 / 指标 / 工具 / 数据结构>
- 白话解释：<一句话>
- 硬件类比：<接口、电源、缓冲区、测试夹具等恰当类比>
- 项目中的位置：<哪条链路、哪个模块、相关文件>
- 技术要点：<保留真实字段、参数、错误码或命令>
- 当前进度：<状态标签 + 已有证据>
- 还缺什么：<未验证范围或未决问题>
- 你需要掌握到什么程度：<识别 / 理解作用 / 能做取舍；通常不要求会实现>
```

## 三、项目落地文件

最小可用版本只需要四个文件：

```text
docs/
└── project-control/
    ├── project-dashboard.md       # 当前驾驶舱，始终只保留最新状态
    ├── session-log.md              # 每次会话的完整交流记录
    ├── decision-log.md             # 需要人决定的事项和原文回答
    └── evidence-index.md           # 测试、实验、报告和证据入口
```

复杂项目再增加：

```text
docs/project-control/
├── stages/                         # 每个阶段的两层阶段卡
├── tasks/                          # 小任务和完成标准
└── glossary.md                     # 项目专用术语白话词典
```

### 文件职责

- `project-dashboard.md`：只放当前状态，不放长篇历史；新会话先读它。
- `session-log.md`：保留用户原话、AI 判断、执行记录和本次结论。
- `decision-log.md`：只记录会改变范围、架构、数据、安全、兼容性或成本的选择。
- `evidence-index.md`：记录每项证据的命令、环境、结果、限制和链接。
- `glossary.md`：一个术语只解释一次，后面直接引用，减少重复学习成本。

## 四、每次会话的固定流程

### 会话开始：只读对齐

把下面这段放进每次复杂任务的开头：

```text
开始前不要修改文件。先读取项目 Agent 规则、PRD/需求、当前驾驶舱、相关任务和证据索引。
用“项目驾驶舱 + 测试站证据”的两层格式汇报：
1. 我们现在在哪里；
2. 当前唯一主任务；
3. 已证实、待证据、待决策、待开发分别有哪些；
4. 这次准备读取或修改哪些文件；
5. 完成标准和停止条件是什么。
所有技术术语首次出现时，保留英文原词或缩写，并给出白话定义、项目例子、忽略它的后果和当前状态。驾驶舱每次最多引入 1–3 个新术语；详细解释写入术语学习卡或 `glossary.md`。
如果涉及产品范围、数据边界、安全、协议、兼容性或成本，先提出一个问题等待确认，不要自行默认。
```

### 会话执行：小步、可验证

```text
一次只推进一个主任务；先计划，再修改；每个小步骤后运行最小验证。
不要用测试改成通过来掩盖行为问题；如果发现计划、代码和文档冲突，先登记冲突。
不要把本机实验、静态检查或单个场景通过表述成完整产品或生产就绪。
```

### 会话结束：证据和交接

```text
结束前必须运行与本任务匹配的检查，并更新驾驶舱、会话日志和证据索引。
用两层格式汇报：做了什么、改了什么、测试结果、证据位置、能证明什么、不能证明什么、剩余风险、下一步和完成标准。
把“待开发 / 待证据 / 待决策 / 被外部条件阻塞”分开写。
如果没有可靠证据，不要使用“已完成”“已解决”“生产可用”。
```

## 五、如何判断协议是否真的在工作

运行一个月后，用下面的问题检查：

- 新会话是否能在 1–3 分钟内说清当前阶段和主任务？
- 用户是否能区分“代码写了”“测试通过了”“产品可以发布了”？
- 每个重要结论是否能找到证据和限制？
- AI 是否在关键决策前停下来询问，而不是替用户选择？
- 换一个模型或换一个 Agent 后，是否还能从仓库继续工作？
- 发生错误时，能否定位是需求、计划、实现、环境还是验证环节的问题？

如果答案多数是否定的，问题通常不是模型能力不够，而是控制文件过长、状态没有更新、完成标准不明确或证据没有接入。

## 六、边界和风险

这个协议不能保证 AI 永远正确。它能做的是让错误更早暴露、更容易定位、更难悄悄变成“已完成”。如果真源本身错误、测试覆盖不足或证据造假，驾驶舱也会忠实地传播错误，因此重要决策仍需要人审阅原始依据。

## 七、最小复用步骤

1. 在目标项目增加 `docs/project-control/` 四个文件。
2. 把会话开始和结束提示词放入项目 `AGENTS.md` 或对应 Agent 的项目规则文件。
3. 先选一个正在进行的任务试运行，不要一次改造整个项目。
4. 每次会话只更新当前驾驶舱和会话日志；证据随测试产生再登记。
5. 连续三次会话后复盘：哪些术语仍难懂、哪些状态容易混淆、哪些证据缺失，再迭代模板。
