# Utell 技术术语学习卡

> 用途：保留专业名词、英文原词和关键参数，同时用项目实例帮助项目拥有者逐步形成技术判断力。
> 学习目标：先能识别和理解作用，再能判断进度与风险；除非当前任务需要，不要求掌握代码实现细节。

## 阅读方法

每个术语按同一条学习路径阅读：

```text
它叫什么
 -> 它是什么
 -> 在 Utell 哪个位置工作
 -> 为什么现在要处理它
 -> 什么证据算完成
 -> 你需要做什么判断
```

## 第一组：读懂当前 G2 阶段

### 1. 技术探针（Technical Spike）

- **它属于什么：** 风险验证方法，不是正式产品功能。
- **10 秒解释：** 用一个有时间限制的小实验，回答某个高风险技术问题“能不能做、边界在哪里”。
- **硬件类比：** 在正式画板和投产前，先用开发板验证芯片在目标电压、温度或总线速率下是否工作。
- **Utell 中的位置：** Phone 的 Noise 互操作实验、Server 的 Relay 本机容量/限流实验，以及后续 ECS 云环境实验。
- **技术要点：** Spike 应有明确问题、测试条件、原始结果、失败样本、结论限制和决策影响；实验代码可以被丢弃。
- **当前进度：** `待证据`。Phone 和 Server 已有部分受控实验结果，但真机生命周期、Connector 共同验收和目标 ECS 证据仍未完成。
- **容易误解：** Spike 通过不等于产品功能完成，也不等于生产可用。
- **你需要掌握：** 能判断实验回答了哪个问题、测试条件是否接近真实环境，以及它有没有被夸大成生产结论。

### 2. Agent/测试脚手架（Harness）

- **它属于什么：** 执行与验证基础设施。
- **10 秒解释：** 把工具、模拟对象、固定输入、测试场景、判定规则和证据收集组织起来，让 Agent 能重复执行和检查工作。
- **硬件类比：** 产线测试夹具加自动测试程序：它负责连接被测设备、施加输入、读取输出、判断合格并保存测试报告。
- **Utell 中的位置：** 两端 `harness/` 下的 `fixtures`、`mocks`、`scenarios`、`scripts`、`evidence` 和公开契约。
- **技术要点：**
  - `fixture`：固定的合成测试输入。
  - `mock/fake`：可控制行为的模拟依赖，例如假 Relay 或假 Connector。
  - `scenario`：Given/When/Then 形式的测试过程。
  - `runner`：实际执行检查的程序。
  - `evidence`：命令、环境、结果、失败样本和校验和组成的证据包。
- **当前进度：** `待开发` + `待证据`。部分语义 runner 已通过，但真实 mock、完整端到端链路、剩余场景和统一证据元数据尚未闭合。
- **容易误解：** Harness 是验证体系，不是产品本体；Harness 场景通过不表示生产应用已经实现同样行为。
- **你需要掌握：** 能询问“测的是规则、模块还是完整产品”“模拟对象是否足够接近真实依赖”“失败时是否留下了可复盘证据”。

### 3. 跨端集成配置（integration-profile）

- **它属于什么：** 版本化、机器可读的跨端公开契约入口。
- **10 秒解释：** Phone、Relay、Connector 共同遵守的“插头尺寸、电压和通信规则总表”。
- **硬件类比：** 一份同时规定连接器引脚、电平、时序、错误处理和兼容版本的接口规范。
- **Utell 中的位置：** 两端 `harness/契约/integration-profile.yaml`；它引用握手、消息封套、错误码、Projection、Card Command 和兼容范围等规则。
- **技术要点：**
  - `profile_version`：该配置的版本号。
  - `status: pending`：仍在讨论或实验，不能作为生产实现依据。
  - `status: approved`：各方已签收，才允许用于正式实现和契约测试。
  - `SHA-256`：文件内容指纹，用于确认两端拿到的是否逐字节相同。
- **当前进度：** `待决策` + `待证据`。两端文件和 SHA-256 一致，但当前仍为 `pending`；一致只能证明“拿的是同一份草案”，不能证明草案已经正确或三端已经互通。
- **容易误解：** 文件一致不等于契约获批；契约获批也不等于所有生产实现已经完成。
- **你需要掌握：** 能判断哪些字段和行为仍未冻结、谁需要签收、状态为什么还不能从 `pending` 改为 `approved`。

## 第二组：理解 Utell 的通信链路

| 专业名词 | 英文与缩写 | 10 秒解释 | Utell 中的作用 | 当前需要注意 |
| --- | --- | --- | --- | --- |
| 中继服务 | Relay | 只负责识别连接并转发密文的云端路由站 | 连接 Phone 与 Connector；不解密业务正文 | Relay 收到不代表 Connector 已收到 |
| 电脑连接器 | Connector | 电脑侧的业务权威入口 | 持久接收、校验、提交数据并生成 Projection | 当前正式工程和公开服务契约仍缺失 |
| 确认回执 | Acknowledgement, `ACK` | 表示某一层“收到”的信号 | Relay ACK 只证明路由层收到密文 | 必须和 Connector 持久接收回执区分 |
| 安全 WebSocket | WebSocket Secure, `WSS` | 运行在 TLS 上的长连接双向通信通道 | Phone/Connector 通过 Relay 持续收发封套 | WSS 保护传输段，不替代应用层 E2EE |
| 端到端加密 | End-to-End Encryption, `E2EE` | 只有通信两端能读明文 | Phone 与 Connector 加解密，Relay 只见密文 | 需要密钥存储、身份绑定和互操作证据 |
| Noise 协议框架 | Noise Protocol Framework | 用标准组合建立加密会话的框架 | 当前选择 `Noise_XX_25519_ChaChaPoly_SHA256` | Spike 可行，仍缺 Connector 共同签收和真机证据 |
| 投影/读取模型 | Projection / Read Model | 从权威数据生成、适合手机展示的视图 | Connector 下发 Card Projection，Phone 只收更高 `event_version` | Projection 不是权威数据库，也不在 Phone 持久化 |
| 预期版本 | `expectedVersion` | 写入时声明“我是基于哪个版本操作的” | Card Command 用它检测并发修改 | 不一致时返回 `VERSION_CONFLICT`，不能自动覆盖 |

## 第三组：理解容量证据

| 指标 | 英文全称 | 白话解释 | 为什么重要 |
| --- | --- | --- | --- |
| `P99` | 99th Percentile Latency | 100 次请求中，约 99 次不超过的延迟边界 | 平均值正常时，它仍能暴露少量特别慢的请求 |
| `RSS` | Resident Set Size | 进程实际占用的物理内存 | 判断并发升高时服务是否持续吃内存 |
| `FD` | File Descriptor | 进程打开的连接、文件等系统资源句柄 | WebSocket 长连接多时，FD 可能先耗尽 |
| 背压 | Backpressure | 接收方处理不动时，系统如何限制发送速度或丢弃工作 | 防止慢 Connector 拖垮整个 Relay |

这些指标当前主要属于 Server ECS 容量 Spike 的 `待证据` 项。知道名词还不够，必须同时记录测试机器配置、连接数、消息大小、持续时间和通过阈值。
