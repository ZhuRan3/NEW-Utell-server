# Utell 人与 AI 开发进度交流记录

> 文档用途：记录用户与 AI Agent 关于 Utell 项目开发过程的交流、思考、资料复核、阶段判断和下一步行动。
> 维护原则：保留用户原话；把事实、推断、建议和待确认问题分开；每次讨论都用普通语言说明“现在在做什么、为什么做、做到什么算完成、下一步是什么”。
> 首次建立：2026-08-25（Asia/Shanghai）

## 0. 使用说明

这不是 PRD，也不是代码设计文档。它更像项目的“驾驶舱日志”：帮助项目拥有者在 AI 执行大量技术工作时，随时知道项目处于哪一段、AI 正在做哪件事、已经有何证据、哪里仍然只是猜测。

每次更新至少包含：

1. 本次用户提出了什么。
2. AI 用了哪些本地文件、外部资料或测试证据。
3. 用非专业术语说明当前结论。
4. 明确区分：已证实、暂时判断、待用户决定、被阻塞。
5. 给出下一步和“完成标准”，而不是只给一串技术名词。

## 2. 本地项目背景快照

### 2.1 旧项目：`utell-develop-release`

这是一个已有较多代码、文档、测试和 Harness 资产的 Flutter + Go 全栈项目。它包含渐进式文档导航、产品/功能地图、执行计划、测试与运行证据、设备控制 Harness，以及前后端代码。它的成熟点不只是代码量，而是已经形成了“用户意图 -> 功能 -> 规格 -> 计划 -> 执行/验证”的生产方法。

### 2.2 新项目：`NEW-Utell-phone` 与 `NEW-Utell-server`

两个新仓库从零建立，当前重点是重新确认需求、边界、契约、技术 Spike 和 Harness，而不是直接复制旧代码。两端的共同工作链路是：

```text
用户需求
  -> PRD / Q&A / 需求台账
  -> 架构边界
  -> 跨端公开契约
  -> Spike（先验证高风险假设）
  -> Harness 场景、fixture、mock、证据
  -> 生产工程骨架
  -> 纵向功能切片
  -> 集成、发布与运维证据
```

### 2.3 对项目拥有者最重要的一句话

新项目目前不是“什么都没做”，也不是“已经可以开发产品”。它已经完成了大量规则、需求语义和验证骨架工作；但几个关键跨端输入还没有被共同签收，因此生产代码尚未获得开工许可。

### 2.4 G0–G5 阶段的人话版

| 阶段 | 工程名称 | 人话解释 | 当前状态 | 进入下一站还缺什么 |
| --- | --- | --- | --- | --- |
| G0 | 真源同步 | 确认两边看的产品说明是不是同一份 | 第一轮完成 | 持续防止文档漂移 |
| G1 | 需求与决策对齐 | 把“想做什么、不能做什么、谁负责什么”逐项问清楚 | 当前批次完成 | Connector 共同确认正式接口 |
| G2 | 技术 Spike | 用小实验验证高风险想法能不能工作 | 进行中 | 真机 Noise 互操作、ECS 容量/背压等证据 |
| G3 | 公开契约冻结 | 把手机、Relay、Connector 之间的“插头标准”定稿 | 未开始；`pending` | 字段、错误、版本和兼容范围获批 |

## 3. 外部资料复核（第一轮）

### 3.1 OpenAI：Codex 长任务与 Harness Engineering

- [Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)
- [Run long horizon tasks with Codex](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)
- [Codex best practices](https://developers.openai.com/codex/learn/best-practices)

**资料给出的做法：**

- 人负责目标、产品判断和架构边界；Agent 负责执行、测试、修复和重复劳动。
- 长任务不能只靠聊天上下文，要有持久化的计划文件和阶段里程碑。
- 每个里程碑都运行验证，不把“代码写完”当成“事情完成”。
- 让应用、日志、指标、测试结果都能被 Agent 读取，形成“执行 -> 观察 -> 修复”的反馈回路。
- 把团队的质量偏好写成仓库规则，并持续扫描偏离，避免 AI 产生的杂乱逐渐积累。

**对你的直接启发：**

你已经有 PRD、Q&A、Harness 和证据；缺少的是面向你的“人类摘要层”。它要在每次 AI 汇报时回答四个问题：正在解决哪一个问题？这一步不做会有什么风险？现在拿到了什么证据？还缺什么才能进入下一阶段？

### 3.2 Anthropic：用上下文、计划和验证控制 Agent

- [Claude Code best practices](https://docs.anthropic.com/en/docs/claude-code/best-practices)
- [Building effective agents](https://www.anthropic.com/research/building-effective-agents)

**资料给出的做法：**

- 给 Agent 最相关的上下文和明确边界，避免把一堆长期规则塞进每次提示词。
- 复杂任务先计划、再执行；让 Agent 在动手前暴露假设和不确定性。
- 使用简单、可观测、可逐步验证的工作流；只有确实需要时再增加多 Agent 编排。
- 让工具返回结构化结果，并保留中间状态，便于恢复和审查。

**对你的直接启发：**

你不需要学习所有软件术语；你需要要求 Agent 先把“假设”翻译成可回答的问题。例如“乱序窗口待冻结”必须解释为：“网络延迟导致消息前后到达时，系统允许暂时等几条消息？超过这个范围怎么办？”

### 3.3 GitHub / Spec Kit：需求驱动，而不是聊天驱动

- [GitHub Spec Kit](https://github.com/github/spec-kit)
- [Spec-driven development with AI](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)
- [Diving Into Spec-Driven Development With GitHub Spec Kit](https://developer.microsoft.com/blog/spec-driven-development-spec-kit/)

**资料给出的做法：**

```text
需求/动机 -> 技术方案 -> 小任务 -> 单独实现与测试 -> 逐项验收
```

核心不是文档多，而是每个小任务都能回答“做什么、如何验证、完成后留下什么证据”。人的角色是掌舵和签收，Agent 负责把已经明确的任务实现出来。

### 3.4 GitHub 社区与开源实践：证据台账、阶段门和轨迹摘要

公开 GitHub 主题和项目中反复出现的共同做法包括：

- `source-of-truth`：保留一份活的真源目录，记录“有什么、为什么存在、哪些规则适用”。
- `loop engineering`：把 Agent 工作变成可重复循环：发现工作 -> 执行 -> 验证 -> 持久化状态 -> 决定下一步 -> 必要时升级给人。
- `human-in-the-loop`：在阶段转换处设置人工签收，不让 Agent 自己把 `pending` 改成 `approved`。
- `evidence ledger`：每个“完成”都必须有命令、环境、输入摘要、结果、失败样本和影响说明。
- 轨迹提炼：不要求人阅读完整 Agent 操作日志，而是提取少量高价值信号：改了什么、为何改、验证了什么、仍有哪些未知。

这些是社区实践的归纳，不等于每个项目都已验证成熟；因此本记录把它们作为方法候选，仍需结合 Utell 的风险和你的理解成本调整。

**共同点：**

- Kimi 明确把计划和执行分开：先调查、画上下文地图、提出方案，得到批准后再改文件和运行检查。
- GLM 官方学习资料把 Agent 循环概括成“获取上下文 -> 执行操作 -> 验证结果”，并建议复杂任务先进入只读 Plan Mode；它还把任务上下文、项目上下文、环境上下文分开。
- MiniMax Code 把任务历史、进度、代码审查和权限控制做成产品内的固定入口；这说明“可回看、可审查、可批准”不是附加功能，而是长期 Agent 工作的基本设施。
- Gemini CLI 的 Plan Mode 是只读的，并且有工具限制、协作编辑和 checkpoint 等配套，目标是让用户先看行动方案，再开放修改权限。
- Kimi CLI 社区仍有人专门请求“执行前预览并批准计划”，说明用户对阶段控制和行动透明度的需求是普遍问题，不是你的个人能力不足。

**对 Utell 的具体启发：**

1. 交流文档应同时记录“项目阶段”和“当前会话任务”，两者不能混为一谈。
2. 任何会改 PRD、契约、数据边界或安全语义的动作，先只读分析，再让你确认，最后才允许执行。
3. 每个长任务应有任务编号、计划、变更清单、验证命令、结果和下一步；换模型或换会话也能接着看。
4. 需要把“批准”从一句模糊的“好的继续”变成明确对象：批准哪一份计划、允许改哪些文件、哪些决策仍不能自行改变。

**资料边界说明：** 本轮没有找到 MiniMax 或 GLM 官方材料专门讨论“非软件背景项目拥有者如何理解进度”。它们提供的是工作流、任务历史、评审、Plan Mode 和上下文管理能力。因此，面向你的“白话控制层”是我们基于多家资料和你的项目情况做出的设计，不冒充厂商原生功能。

## 4. 初步结论：你缺的不是更多技术，而是“可理解的控制面”

### 4.1 当前工作链路的优点

- 有明确的文档真源层级，减少 AI 自行猜测。
- 有阶段门 G0–G5，避免直接从 PRD 跳到生产代码。
- 有 Spike、fixture、场景和证据，开始把“我觉得可以”变成可复核结果。
- 有两端契约同步规则，避免 Phone、Relay、Connector 各写一份协议。
- 旧项目已经证明你具备较强的 Harness 和全流程自动化能力。

### 4.2 当前工作链路对你的缺口

- 阶段名称是工程语言，没有“这对产品意味着什么”的一句话解释。
- “进行中”混合了三种完全不同的状态：正在做、等待你决定、等待外部证据。
- 通过的 Harness 场景容易被误读成产品已经完成；需要显式区分“语义检查通过”和“生产功能可用”。
- 下一步列表偏长，没有标出唯一的当前主任务，以及完成它需要谁提供什么。
- 技术名词没有固定的“小白解释”和生活化例子，导致每次会话都重新付出理解成本。

## 5. 建议采用的“人类可读进度协议”

以后每个开发会话的开头和结尾，都使用下面这张卡片。它是交流协议，不替代现有工程文档。

### 5.1 当前状态卡

| 字段 | 必须用普通话回答 |
| --- | --- |
| 我们要解决什么 | 用一句用户能感受到的话描述 |
| 当前阶段 | 例如：正在验证网络断开后是否会丢数据 |
| 这一步为什么重要 | 不做会造成什么现实风险 |
| 已经完成 | 只写有文件、命令或测试结果支持的事实 |
| 还没完成 | 明确是“待开发 / 待决策 / 待外部证据”哪一种 |
| 当前唯一主任务 | 下一步只推进哪件最重要的事 |
| 完成标准 | 满足什么条件才算从当前阶段毕业 |
| 需要用户回答 | 最多一个问题；没有就写“无需回答” |
| 风险等级 | 低 / 中 / 高，并解释后果 |

### 5.2 四种状态的含义

- **已证实**：有代码、测试、运行结果或双方签收记录支持。
- **暂时判断**：Agent 的合理推断，仍可能被新证据推翻。
- **待你决定**：技术上有多个可行选项，取舍会影响产品行为或成本。
- **被阻塞**：不是 AI 不会做，而是缺少前置输入、外部环境或共同 Owner。

### 5.3 技术词翻译规则

以后首次出现术语时，必须同时给出：

1. 一句话定义。
2. 一个 Utell 里的具体例子。
3. 不处理它会怎样。
4. 当前是已确认还是待确认。

例如：

> **契约（contract）**：手机和服务器约定的“消息格式与行为规则”，像插头的尺寸和电压标准。Utell 里它规定手机发什么、Relay 回什么、Connector 如何确认收到。它没冻结前，两边各自写代码很容易互相接不上。目前 `integration-profile` 仍是 `pending`，所以只能用于讨论和 Spike。

### 5.4 示例：把当前 G2 技术 Spike 讲成人能控制的工作

**任务名称：** 验证 Relay 在受控压力下能否维持安全路由。

**硬件工程类比：** 这像给电源模块做温升和负载实验。实验通过，说明在给定电压、负载和环境下工作；它不等于已经拿到整机量产认证。

**我们现在实际做的事：**

- Phone 侧用固定 Noise 测试向量验证加密握手和失败路径。
- Server 侧在本机用 Go/Caddy/SQLite 合成环境验证限流、并发和 WSS 反代保护。
- Harness 用合成输入检查 READY、ACK、未知结果、Projection 版本排序、版本冲突和重放/篡改/过期等规则。

**这些结果能够证明：** 某些规则在受控环境中是可执行、可重复检查的。

**这些结果不能证明：** 真机后台恢复一定正常；Connector 已经存在并能互操作；阿里云 ECS 在目标容量下足够稳定；生产数据库已有备份和回滚能力；产品已经可以发布。

**G2 当前毕业条件：** 高风险假设有原始结果、失败样本、解释和决策影响；真机和目标 ECS 的关键证据补齐；Connector Owner 对互操作向量共同签收。

**当前唯一主任务（建议）：** 先把 Connector Service 的 Owner、边界和公开接口范围说清楚。原因很简单：Phone 和 Relay 后续很多字段都要围绕 Connector 的权威行为对接；如果这个“另一头的插座”还没人负责，继续细化生产字段会反复返工。

### 5.5 两层结合的固定格式

#### 第一层：项目驾驶舱（先看这一层）

这一层只解决“我们在哪里、为什么停在这里、下一站是什么”。默认控制在一屏内。

| 项目 | 示例 |
| --- | --- |
| 当前所在阶段 | G2 技术 Spike：验证关键想法能否工作 |
| 当前一句话状态 | 已完成受控实验，正在补齐真机、云环境和 Connector 证据 |
| 当前主任务 | 明确 Connector Owner、边界和公开接口范围 |
| 已经走过的路 | G0 第一轮同步完成；G1 当前批次完成；部分 G2 实验通过 |
| 前方路障 | `integration-profile` 仍是 `pending`；缺少共同验收和生产环境证据 |
| 下一站 | G3：冻结 Phone、Relay、Connector 的公开通信规则 |
| 能否继续 | 暂不能进入生产工程；可以继续做 G2 证据和边界确认 |
| 需要用户做什么 | 只在出现“待你决定”时回答一个具体问题 |

#### 第二层：测试站记录（需要核对时再看）

这一层回答“测了什么、怎么测、结果能证明什么”。它保留工程依据，但每一项都配白话解释。

| 项目 | 必须记录 |
| --- | --- |
| 测试目的 | 要验证的一个具体风险或假设 |
| 测试条件 | 设备、软件版本、网络、并发量、输入类型等 |
| 操作步骤 | Agent 实际运行的命令或操作 |
| 观察结果 | 原始结果摘要，包含通过和失败样本 |
| 证据位置 | 文件路径、日志、截图、测试报告或提交号 |
| 可以证明什么 | 结果成立的范围 |
| 不能证明什么 | 尚未覆盖的环境、规模或边界 |
| 放行标准 | 满足什么条件才能进入下一阶段 |
| 决策影响 | 通过、继续补证据、修改方案或停止 |
| 回滚方式 | 如果结论被推翻，回到哪个文档或阶段 |

#### 状态标签

所有阶段卡和会话汇报统一使用以下四个标签，防止“进行中”掩盖不同原因：

- `已证实`：有可定位的代码、测试、运行结果或 Owner 签收。
- `待证据`：方向暂时合理，但还缺实验、真机、云环境或集成结果。
- `待决策`：存在多个合理选项，需要你决定产品取舍。
- `待开发`：方向已确认，但还没有实现。

| G5 | 验证生产工程是否能构建、启动并完成首个真实闭环 | 构建日志、部署记录、健康检查、纵向切片结果 | 工程具备可运行的最小产品骨架 | 还不能替代完整发布和长期运维验证 | Phone/Relay/Connector 可构建；同一契约完成首个纵向切片；发布门禁通过 |

**硬件类比：** G0/G1 像确认原理图和接口定义；G2 像实验室可行性与边界测试；G3 像冻结连接器和电气规范；G4 像自动化产线测试夹具；G5 才像装配第一台可运行样机。任何一站的测试通过，都不能替代其他站的测试。

## 6. 本轮交流的第一条教学结论

你现在不需要先学会 Go、Swift、Noise 或 WebSocket，才能掌握项目方向。你需要先掌握一套“项目状态语言”：

```text
目标是什么
 -> 当前只验证哪一个假设
 -> 证据是什么
 -> 证据能证明什么、不能证明什么
 -> 谁来决定下一步
 -> 什么条件满足后才允许继续
```

这套语言像硬件工程里的测试点和验收门。你不必亲自设计每个芯片内部电路，但必须知道当前测的是电源、时钟还是通信，以及示波器上的波形能证明什么、不能证明什么。

## 8. 记录 003：为什么这样做，以及如何复用

**日期：** 2026-08-27

**用户问题：**“请你给我解释你这么做的原理和效果，还有我需要怎么才能把这个东西复用在实际开发的项目当中，让它也能这么跟我沟通交流。”

### 8.1 原理：给 Agent 增加一层“可理解控制面”

这套方法不是让模型凭空变得更准确，也不是再写一份更长的提示词。它是在工程真源和人类理解之间增加一个稳定的翻译层：

```text
代码 / PRD / 契约 / 测试 / 日志
              ↓ 提取事实、翻译术语、标出边界
驾驶舱摘要 + 测试站证据
              ↓ 用户批准、补充信息或暂停
下一步 Agent 行动
```

它依赖六个部件：

1. **真源**：产品和工程事实必须有出处，不能只存在于聊天记忆里。
2. **状态机**：用 `已证实`、`待证据`、`待决策`、`待开发` 区分不同类型的“未完成”。
3. **证据边界**：每个结论都写“能证明什么”和“不能证明什么”。
4. **阶段门**：进入下一阶段需要满足明确条件，Agent 不能自行宣布放行。
5. **角色分工**：用户负责目标、取舍和放行；Agent 负责执行、验证和报告；自动测试提供反馈。
6. **渐进式披露**：先给一屏方向摘要，用户需要时再展开命令、日志和原始证据。

### 8.2 效果：把“相信 AI”改成“检查 AI 的工作”

| 原来的问题 | 协议带来的变化 |
| --- | --- |
| AI 说了一大段专业结论，但不知道现在在干什么 | 先显示阶段、主任务和下一站 |
| “进行中”可能代表开发、等待决策或缺证据 | 用四种状态标签拆开 |
| 测试通过容易被误解为产品完成 | 强制写明证据范围和不能证明的部分 |
| 换模型或新会话后上下文丢失 | 状态、计划、决策和证据写入项目文件 |
| AI 可能在关键处自行猜测 | 涉及范围、安全、协议等事项必须先停下来问一个问题 |
| 人必须阅读完整操作轨迹 | 只看摘要，需要时再定位原始证据 |

它的实际目标不是消灭错误，而是让错误更早暴露、更容易定位、更难伪装成“已完成”。它也不能修复错误的 PRD、缺失的测试或不可靠的证据；因此重要判断仍要回到原始依据。

### 8.3 如何复用到其他项目

已经新增可复制模板：[AI协作进度协议.md](./可复用模板/AI协作进度协议.md)。Phone 和 Server 两端同路径文件已逐字节同步。

最小落地只需要五步：

1. 在项目中建立 `docs/project-control/`，放置 `project-dashboard.md`、`session-log.md`、`decision-log.md` 和 `evidence-index.md`。
2. 把模板中的“会话开始”和“会话结束”提示词加入项目的 `AGENTS.md`、`CLAUDE.md` 或其他 Agent 项目规则文件。
3. 先选一个真实任务试运行，不要一开始改造全仓库；复杂任务必须先只读调查和计划。
4. 每次会话开始先读驾驶舱，结束时更新驾驶舱、会话记录和证据索引。
5. 连续运行三次后复盘：哪些术语仍然难懂、哪些状态容易混淆、哪些证据缺失，再修改模板。

### 8.4 可以直接复制的会话开场白

```text
开始前不要修改文件。先读取项目规则、需求真源、当前驾驶舱和相关证据。
请先用两层格式汇报：第一层是项目驾驶舱，说明我们在哪里、当前唯一主任务、前方路障和下一站；第二层是测试站证据，说明已经证实什么、还缺什么、完成标准是什么。
复杂任务先给计划，等待我确认后再执行。专业名词不要全部口语化或省略；首次出现时保留中文、英文全称或缩写，并用白话解释、项目例子、忽略后果和当前证据状态说明。驾驶舱每次最多介绍 1–3 个新术语。
涉及产品范围、数据边界、安全、协议、兼容性或成本时，一次只问我一个问题，不要自行默认。
```

### 8.5 可以直接复制的会话结束语

```text
结束前请运行与本任务匹配的检查，并更新项目驾驶舱、会话日志和证据索引。
请按两层格式汇报：做了什么、改了什么、测试结果、证据位置、证据能证明什么、不能证明什么、剩余风险、下一步和完成标准。
请严格区分已证实、待证据、待决策、待开发；没有可靠证据时不要使用“已完成”“已解决”或“生产可用”。
```

### 8.6 复用时最重要的三个注意事项

- 不要把驾驶舱写成新的 PRD；它只记录当前状态和证据入口。
- 不要只记录百分比；“完成 80%”必须拆成哪些阶段已通过、哪些风险仍未验证。
- 不要让 Agent 自己修改放行状态；阶段门的通过需要证据，涉及产品和架构取舍时需要用户签收。

### 9.3 这三个词如何串成当前开发路径

```text
Technical Spike
先证明高风险方案在指定条件下可行
        ↓
Harness
把已经明确的规则变成可重复运行、可故障注入的检查
        ↓
integration-profile approved
三端共同签收正式接口和行为规则
        ↓
生产工程与跨端实现
```

因此，当前不是在“漫无目的写文档”，而是在完成生产编码前的三件事：用 Spike 排除不可行方案，用 Harness 建立验证能力，用 integration-profile 冻结三端不会各写各的接口。

### 9.4 技术学习深度

以后每个术语会明确你需要学到哪一层：

1. **识别层**：看到 `ACK`、`WSS`、`E2EE` 时知道它大概是什么。
2. **作用层**：知道它在 Utell 链路中负责什么、上下游是谁。
3. **判断层**：知道什么证据算通过、什么结论属于夸大。
4. **实现层**：能够编写协议或代码；只有你主动希望深入时才展开。

当前目标是让你稳定达到第 2–3 层，而不是强迫你掌握每个框架的代码实现。
