# 人类可读进度与技术沟通规范

> 状态：强制执行（2026-08-27）
> 适用范围：本仓库所有 Agent、自动化任务、开发会话、审计、Spike、Harness、构建、部署和发布工作。
> 同步要求：本文件在 NEW-Utell-phone 与 NEW-Utell-server 两端必须逐字节一致；修改共同规则时同一工作批次同步。

## 1. 目的

本规范解决一个明确问题：Agent 可以执行复杂的软件工程工作，但项目 Owner 不应因为不熟悉软件专业术语而无法知道“现在在做什么、为什么做、做到什么算完成、下一步是什么”。

本规范不是 PRD、架构设计或测试报告，而是连接工程真源与人类判断的强制沟通层。它必须同时满足：

- 保留专业名词、英文原词、缩写、字段、参数、命令和技术要点。
- 用循序渐进的教学解释这些内容，使 Owner 能理解其作用和风险。
- 用阶段、证据和放行条件表达进度，不用没有依据的百分比代替。
- 让新会话、新模型和新 Agent 可以从仓库文件恢复上下文。

## 2. 强制性词语和角色

本文件中的“必须/不得”是硬性门禁；“建议”是未改变产品和工程边界的工作建议。

### 2.1 Owner 必须保留的权力

Owner 负责目标、产品取舍、风险接受、跨端职责、公开契约批准和阶段放行。Agent 不得替 Owner 把 `待决策` 改为“已确认”或把阶段改为“已通过”。

### 2.2 Agent 必须承担的责任

Agent 必须读取相关真源，先计划后执行，运行与任务匹配的验证，保存证据，说明限制，更新进度和交流记录。Agent 不得用专业术语堆砌来替代解释，也不得把合理推测写成事实。

### 2.3 自动化工具的责任

测试、构建、Harness、CI、设备或 staging 环境负责提供可重复的反馈信号。工具通过只代表它覆盖的范围通过，不自动代表产品、阶段或发布通过。

## 3. 强制文档结构

每个采用本规范的项目必须建立以下控制文件；跨仓库项目可约定一个共享的主交流记录，但每个仓库都必须有入口和本端驾驶舱：

```text
文档/交流记录/
├── README.md                         # 本端入口、真源位置和更新规则
├── 项目驾驶舱.md                     # 当前最新状态，面向 Owner 的一屏摘要
├── 技术术语学习卡.md                 # 中文、英文、作用、证据和判断层级
├── 可复用模板/AI协作进度协议.md       # 两层协议和会话模板
└── 原始消息/                         # 用户原文或外部输入，按需建立
```

若项目已有一份 canonical `人与AI开发进度交流记录.md`，不得另建第二份相互独立的总记录；`README.md` 必须链接主记录并说明谁负责更新。

其他工程真源仍按既有规则维护：

```text
PRD / 需求问答记录 / 需求确认台账
  -> 架构与契约
  -> 技术选型与 Spike
  -> Harness 契约 / fixtures / mocks / scenarios
  -> 测试证据与发布门禁
  -> 项目驾驶舱 / 会话记录 / 决策记录
```

交流记录不能反向替代 PRD、契约、测试或发布门禁；如果两者冲突，必须登记冲突并回到权威真源解决。

## 4. 强制两层汇报格式

### 4.1 第一层：项目驾驶舱

每个复杂会话开始和结束都必须先给驾驶舱摘要，默认控制在一屏内，至少包含：

```markdown
## 驾驶舱摘要

- 我们在哪里：<阶段 / 任务>
- 我们要解决什么：<一句 Owner 能理解的话>
- 当前一句话状态：<已完成什么，正在等什么>
- 当前唯一主任务：<现在只推进哪一件事>
- 已经走过的路：<完成的阶段或里程碑>
- 前方路障：<阻塞 / 待证据 / 待决策>
- 下一站：<下一阶段及目的>
- 能否继续：<可以继续 / 需要确认 / 暂停>
- 需要 Owner 回答：<最多一个问题；没有则写“无需回答”>
```

驾驶舱必须明确“能否继续”，不得只输出任务清单。它必须让 Owner 能区分：可以执行、等待证据、等待决策、被外部条件阻塞。

### 4.2 本次技术学习条

驾驶舱中每次最多引入 1–3 个新专业名词；已经解释过的词可以直接使用，但原始英文、缩写和字段必须保留：

```markdown
### 本次技术学习条

| 专业名词 | English / Acronym | 10 秒解释 | 在本项目中的作用 | 当前状态 |
| --- | --- | --- | --- | --- |
| <术语> | <原词> | <一句白话> | <模块 / 链路 / 决策> | <状态标签> |
```

### 4.3 第二层：测试站证据

需要核对时，必须展开测试站记录：

| 项目 | 必须记录 |
| --- | --- |
| 测试目的 | 要验证的一个风险或假设 |
| 测试条件 | 设备、版本、网络、输入、规模和权限 |
| 实际操作 | Agent 执行的命令或步骤 |
| 观察结果 | 通过、失败、异常和失败样本 |
| 证据位置 | 文件、日志、截图、报告、提交号或校验和 |
| 可以证明什么 | 结果成立的范围 |
| 不能证明什么 | 未覆盖的环境、规模、实现或发布条件 |
| 放行标准 | 下一阶段必须满足的门槛 |
| 决策影响 | 继续、补证据、改方案、暂停或回滚 |
| 回滚方式 | 结论被推翻时回到哪个文件或阶段 |

## 5. 专业名词教学要求

### 5.1 首次出现的术语

专业名词不得全部替换成口语，也不得只给名词不解释。首次出现必须按以下顺序说明：

1. 中文名称、English full name、缩写或真实字段。
2. 它属于什么：协议、服务、指标、工具、数据结构或流程。
3. 10 秒白话定义。
4. 在当前项目哪一条链路、哪个模块中工作。
5. 忽略它会有什么后果。
6. 当前是 `已证实`、`待证据`、`待决策` 还是 `待开发`。
7. 已有证据、缺失证据，以及 Owner 需要掌握到哪一层。

### 5.2 学习深度

默认目标是让 Owner 达到“作用层 + 判断层”，不强迫 Owner 立即掌握实现层：

- 识别层：看到 `ACK`、`WSS`、`E2EE` 能知道大概是什么。
- 作用层：知道它在链路中的位置、上下游和职责。
- 判断层：知道什么证据算通过、哪些结论被夸大。
- 实现层：理解字段、算法、代码结构并能参与实现；只有任务需要或 Owner 主动要求时展开。

### 5.3 技术学习卡

需要深入时，在 `文档/交流记录/技术术语学习卡.md` 增加：定义、硬件类比、项目位置、真实技术要点、当前进度、证据边界和掌握目标。学习卡不得虚构未冻结字段或把建议写成决策。

## 6. 状态和阶段门

### 6.1 四种强制状态

- `已证实`：有可定位代码、测试、运行结果或 Owner/跨端 Owner 签收。
- `待证据`：方向暂时合理，但缺实验、环境、集成或容量证据。
- `待决策`：存在多个合理方案，需要 Owner 选择取舍。
- `待开发`：方向已经确认，但尚无实现或可运行产物。

不使用没有定义的“差不多”“基本完成”“进行中”作为唯一状态。可以使用这些词作补充，但必须同时给出四种强制状态之一。

### 6.2 阶段状态不能互相替代

- Spike 通过：只证明指定实验条件下的高风险假设可行。
- Harness 场景通过：只证明指定规则可被重复检查。
- 契约文件一致：只证明文件内容相同，不证明契约已批准或实现已互通。
- 静态检查通过：只证明对应检查没有发现问题，不证明功能正确或生产可用。

任何汇报出现“通过”时，必须同时写明通过对象、环境和限制。

## 7. 工具链要求

### 7.1 发现和状态检查

Agent 必须优先使用结构化、可复核的项目工具：

```text
rg --files                         # 盘点文件入口
rg -n "关键词" <paths>             # 定位规则、状态、证据和引用
git status --short                 # 确认工作树和用户已有改动
git diff --check                   # 检查空白和补丁格式
```

不得把未读取的目录、未运行的命令或未观察的页面写成已检查。

### 7.2 当前 Utell Harness 工具

两端适用的共同门禁和 runner：

```text
harness/scripts/verify_contract_gate.sh
ruby harness/scripts/run_ready_scenarios.rb
```

Phone 端按任务选择 Rust/Swift 测试、真机或模拟器检查；Server 端按任务选择 `go test -race ./...`、Relay/Caddy 合成门禁、staging 或 ECS Spike。每次必须记录实际命令、退出结果和环境；命令因缺少 target、依赖、设备或网络而不能运行时，状态写为 `待证据` 或“环境阻塞”，不得写成通过。

### 7.3 证据登记

验证证据必须进入 `harness/evidence/YYYY-MM-DD/` 或明确链接的外部证据包，并包含：提交版本、命令、环境、输入摘要、通过/失败、失败样本、解释、校验和、可证明范围和限制。不得把真实业务正文、私钥、凭据或可还原身份写入证据。

## 8. 会话生命周期门禁

### 8.1 开始前：只读对齐

复杂任务开始时，Agent 必须先读取：本端 `AGENTS.md`、当前 PRD/需求、相关架构/契约、`文档/工作进度/开发进度与会话交接.md`、`文档/交流记录/项目驾驶舱.md`、相关任务和证据索引。未经只读对齐不得修改文件。

开始汇报必须包含驾驶舱、技术学习条、计划修改范围、完成标准和停止条件。

### 8.2 执行中：小步和验证

- 一次只推进一个当前唯一主任务。
- 复杂任务先计划，涉及关键决策时等待 Owner 确认。
- 每个小步骤后运行最小相关验证。
- 发现需求、文档、契约、代码或运行时冲突时先登记，不静默修正。
- 不得用修改测试预期、降低门槛或删除失败样本来制造“通过”。

### 8.3 结束时：交接和记录

结束前必须更新项目驾驶舱、会话日志/主交流记录、技术术语学习卡和证据索引（若本次有对应变化）。结束汇报必须再次使用两层格式，并列出：改动文件、命令和结果、证据位置、能证明/不能证明的范围、剩余风险、下一步、完成标准和是否需要 Owner 决定。

## 9. 重大事项和问答门禁

涉及产品范围、数据归属、离线语义、权限、安全、协议字段、错误语义、兼容性、发布承诺、云资源或预算时：

1. 先将问题写入 Q&A 或决策记录。
2. 一次只向 Owner 提出一个独立问题。
3. 给出可理解的选项、取舍、推荐理由和回滚条件。
4. 在答案写入真源前，不得修改生产实现、批准契约或关闭阻塞。

## 10. 禁止事项

- 只报百分比，不报阶段、证据和放行条件。
- 只报英文缩写，不解释其作用和项目位置。
- 把 Spike、Harness、静态检查或本机实验通过写成产品完成或生产可用。
- 把 Relay ACK、文件一致或单个 runner 通过写成业务提交成功。
- 让 Agent 自行批准契约、关闭重大风险或代表 Owner 作产品取舍。
- 为了让驾驶舱变绿而删掉失败证据、改测试预期或把未知结果改成成功。
- 另建一份与主交流记录互相独立、长期漂移的进度文档。

## 11. 最小验收

本规范是否落地，至少检查：

- 新会话能在 1–3 分钟内说明阶段、唯一主任务和下一站。
- 驾驶舱保留专业词、英文和技术参数，同时提供白话解释。
- 每项重要结论都能定位证据并看到限制。
- 关键决策前 Agent 会停下来询问，而不是自行默认。
- 换模型或新会话后可以从项目文件恢复工作。
- 错误能被归类为需求、计划、实现、环境或验证问题。
